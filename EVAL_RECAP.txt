THEORIE  Bases d'un serveur HTTP
────────────────────────────────────────────────────────────────────────────────
  EXPLICATION :
  Un serveur HTTP est un programme qui écoute sur un socket TCP. Il accepte des connexions, lit la
  requête (méthode, chemin, headers, body), construit une réponse (status line,
  headers, body) et la renvoie. Notre serveur supporte HTTP/1.1 avec keep-alive en non bloquanr.

  Cycle complet :
    1. socket() → crée un socket TCP
    2. bind()   → attache au port (ex: 8080)
    3. listen() → met en écoute (backlog = 128)
    4. poll()   → attend une activité sur les fd
    5. accept() → accepte une connexion → nouveau fd client
    6. read()   → lit la requête HTTP
    7. parse    → analyse méthode, chemin, headers, body
    8. build    → construit la réponse
    9. write()  → envoie la réponse
   10. retour à poll()


THEORIE Quelle fonction pour I/O Multiplexing ?
────────────────────────────────────────────────────────────────────────────────
  RÉPONSE : poll()
  Fichier : Webserv.cpp, fonction startListening()

  EXPLICATION : poll() surveille simultanément plusieurs file descriptors (fd).
  On lui passe un tableau de pollfd avec les fd à surveiller et les événements
  attendus (POLLIN = données à lire, POLLOUT = prêt à écrire). Il bloque jusqu'à
  ce qu'un fd soit prêt, ou jusqu'au timeout.


THEORIE : Comment fonctionne poll() (ou select()) ?
────────────────────────────────────────────────────────────────────────────────
  EXPLICATION :
  poll() prend un tableau de struct pollfd { int fd; short events; short revents; }
  et un timeout en ms. Il retourne le nombre de fd prêts.

  struct pollfd fds[N];
  fds[0].fd = listen_fd;  fds[0].events = POLLIN;
  fds[1].fd = client_fd;  fds[1].events = POLLIN | POLLOUT;

  int n = poll(fds, N, timeout_ms);
  // Après poll(), on vérifie fds[i].revents pour savoir qui est prêt.

  Différence avec select() : poll() n'a pas de limite FD_SETSIZE (1024), et
  l'interface est plus claire (pas de fd_set à reconstruire à chaque appel).


THEORIE : Un seul poll() pour accept ET read/write ?
────────────────────────────────────────────────────────────────────────────────
 Oui, un seul poll() dans la boucle principale (Webserv.cpp,
  startListening()). Le même appel surveille :
    - Les fd d'écoute (SOCKET) → POLLIN → accept() → nouveau client
    - Les fd clients (ACCEPT)  → POLLIN (lire requête) | POLLOUT (envoyer réponse)
    - Les fd CGI (PIPE)        → POLLIN/POLLHUP (lire résultat CGI) | POLLOUT (écrire body)

  La boucle principale :
    while (g_listening) {
        poll(m_fds.data(), m_fds.size(), 200);
        for (chaque fd) {
            if SOCKET  → addClient()     // accept
            if ACCEPT  → readQuery()     // read requête
                       → sendQuery()     // write réponse
            if PIPE    → readCGI()       // read sortie CGI
                       → writeCGI()      // write body vers CGI
        }
    }


TEST : poll() vérifie READ et WRITE en même temps ?
────────────────────────────────────────────────────────────────────────────────

  Un seul poll() dans la boucle principale, avec des fds qui ont POLLIN ET
  POLLOUT en même temps — pas deux boucles séparées.

  FLUX :
  1. Nouveau client → pfd.events = POLLIN seulement  (addClient, Webserv.cpp:237)
  2. Réponse prête → m_fds[i].events |= POLLOUT      (startListening, Webserv.cpp:181)
     → le fd a maintenant POLLIN | POLLOUT simultanément
  3. Un seul poll() surveille TOUT :                  (Webserv.cpp:97)
       poll(m_fds.data(), m_fds.size(), 200)
  4. Après poll(), même iteration, même fd :          (Webserv.cpp:144-172)
       if (revents & POLLOUT) → sendQuery(fd)      // envoyer réponse
       if (revents & POLLIN)  → readQuery(fd, ...) // lire requête
     POLLOUT retiré quand tout est envoyé :
       m_fds[i].events &= ~POLLOUT;               (Webserv.cpp:149)

  CE QUI SERAIT GRADE 0 :
    poll(read_fds,  n, t);   // pour les reads
    poll(write_fds, n, t);   // pour les writes (deux appels séparés)

  CE QU'ON FAIT (correct) :
    un seul poll() → revents & POLLIN  ? → read
                   → revents & POLLOUT ? → write

TEST : Vérification des erreurs sur read/recv/write/send
────────────────────────────────────────────────────────────────────────────────
  RÉPONSE : Toutes les valeurs de retour sont vérifiées :
    - n > 0  : données valides, traitement normal
    - n == 0 : connexion fermée par le client → destroyClient()
    - n == -1 avec EAGAIN/EWOULDBLOCK : pas de données dispo (non-blocking) → ok, on continue
    - n == -1 autre erreur → log + destroyClient()

  Code : Webserv.cpp readQuery() lignes ~295-302 et sendQuery() lignes ~337-340


TEST : errno après read/recv/write/send → grade 0
────────────────────────────────────────────────────────────────────────────────
  RÉPONSE : On ne vérifie PAS errno pour décider du comportement du serveur.
  On vérifie la valeur de retour (n). errno est seulement utilisé pour les
  messages de log (strerror(errno)), jamais pour la logique de contrôle.


TEST : Aucun read/write sans passer par poll()
────────────────────────────────────────────────────────────────────────────────
  RÉPONSE : Tous les read() et write() sont dans des branches conditionnelles
  déclenchées par poll(). Il n'y a aucun read/write sur socket en dehors de
  la boucle poll(). Les accès fichiers (ifstream pour lire du HTML) sont hors
  socket → autorisés.

TEST : Même port plusieurs fois dans la config
────────────────────────────────────────────────────────────────────────────────
  Dans other.conf, alpha ET beta déclarent listen 127.0.0.1:8080.
  Le deuxième bind() échoue (EADDRINUSE), createListener() retourne NULL
  silencieusement, le serveur continue avec un seul socket sur 8080.
  Le virtual hosting fonctionne quand même via le header Host.

  EXPLICATION : Notre serveur n'arrête pas le démarrage si un port est
  déjà utilisé — il continue avec les ports qu'il a pu binder.


TEST : Deux instances avec ports en commun
────────────────────────────────────────────────────────────────────────────────
  # Terminal 1
  ./webserv other.conf              # port 8080 + 9090

  # Terminal 2
  ./webserv /tmp/conf_second.conf   # tente 8080 (échoue) + 9999 (succès)

  curl http://localhost:8080/   # → répond le processus 1
  curl http://localhost:9999/   # → répond le processus 2

  EXPLICATION : Le processus 2 démarre car createListener() catch l'exception
  du bind raté sur 8080 et retourne NULL. Il écoute uniquement sur 9999.
  C'est une dégradation gracieuse — mais aucune erreur n'est visible dans les
  logs, ce qui est un point faible à assumer.
